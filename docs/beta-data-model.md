# Beta implementation notes\n\n## Scope of the beta prototype\n\n- No user registration in the first beta flow.\n- Racket setups are user-created documents. The interface does not restrict the number or names of custom components.\n- A new setup can be initialized from a previous setup. The new record is a copy; editing it does not mutate the source record.\n- Default comparison dimensions are provided, while detailed dimensions are optional and extensible.\n- This initial UI prototype persists setup documents in browser localStorage.\n\n## Deployment boundary\n\nThe current GitHub Pages deployment is a static Vite site. It cannot securely write to a server-side database by itself. The current commit is a UI prototype only: server persistence and cross-device synchronization are not active. AWS credentials must never be embedded in browser code.\n\n## Recommended server architecture\n\nUse AWS Lambda + API Gateway + DynamoDB. The browser should obtain a random anonymous installation identity and a signed, scoped token from the API. Validate the token server-side and derive the owner key from the token; never trust an owner ID supplied in a request body.\n\n### DynamoDB single-table design\n\nTable: TennisCompass\n\n| PK | SK | Purpose |\n|---|---|---|\n| OWNER#<anonymousOwnerId> | SETUP#<setupId> | Racket setup document |\n| OWNER#<anonymousOwnerId> | COMPARISON#<comparisonId> | Comparison document |\n| OWNER#<anonymousOwnerId> | PROFILE | Optional owner metadata |\n\nCommon attributes: entityType, createdAt, updatedAt, schemaVersion.\n\nSetup attributes: name, components (arbitrary JSON object), sourceSetupId.\n\nComparison attributes: baseSetupId, targetSetupId, ratings (arbitrary JSON object), note.\n\n### Flexible setup document\n\n```json\n{\n  "schemaVersion": 1,\n  "setupId": "uuid",\n  "name": "My setup",\n  "components": {\n    "racket": "HEAD Radical MP",\n    "string": "Lynx Tour",\n    "gauge": "1.25 mm",\n    "tension": { "main": "45 lbs", "cross": "43 lbs" },\n    "custom": [{ "name": "overgrip", "value": "..." }]\n  },\n  "sourceSetupId": null,\n  "createdAt": "ISO-8601",\n  "updatedAt": "ISO-8601"\n}\n```\n\nKeep stable envelope fields (IDs, timestamps, schema version and ownership) while allowing arbitrary user-defined component data. NoSQL flexibility does not mean removing all structure.\n\n### Flexible comparison document\n\n```json\n{\n  "schemaVersion": 1,\n  "comparisonId": "uuid",\n  "baseSetupId": "uuid",\n  "targetSetupId": "uuid",\n  "ratings": [{\n    "category": "ballSpeed",\n    "label": "ボールスピード",\n    "value": "+",\n    "details": [{ "label": "フラット", "value": "." }]\n  }],\n  "createdAt": "ISO-8601"\n}\n```\n\n## Initial rating dimensions\n\n1. ボールスピード\n2. パワー\n3. スピン\n4. コントロール\n5. 打球感\n\nScale: ++ / + / . / - / --.\n\nDetailed dimensions are user-defined, not a closed enum. Examples: ball speed and power—フラット、ドライブ、トップスピン、スライス; spin—トップスピン、スライス; control—方向、深さ、高さ; feel—強打時、タッチ時、ボレー時.\n\n## Anonymous-user recovery\n\nWithout registration, browser identity is not a durable account identity. Clearing browser data or changing devices can lose the local copy. Server persistence can support recovery only through a retained recovery key or an explicit device-transfer flow. A public unauthenticated write API would permit abuse and data tampering; it is not an acceptable substitute for anonymous authentication.
